# Opt-in XMage adapter

Source pin: Adamychen/xmage-nexus at `825d1205acca114825f235c6993f1e5a6a6db9fa`.
Entry point: `mage.player.ai.ComputerPlayerFourthSeat` (standard name/range/skill constructor).
This is a separate experimental class extending basic `ComputerPlayer`, not MAD/ComputerPlayer7.
No default player registration, launcher, existing engine, deployment or runtime configuration changes are included.

## Isolated build

Run `MAVEN=/path/to/mvn ./scripts/build-adapter.sh /path/to/pinned/xmage /new/disposable/build` from this experiment.
The script verifies the exact commit, archives it to a new directory, overlays policy and adapter sources in the basic AI module, then builds the module with its real dependencies. It refuses an existing output directory and does not modify its input checkout. Maven's local dependency repository is inside that disposable directory. Build requires Java, Maven and access to dependencies. Compiling is not game validation.

The output jar contains both existing basic AI and the new class. Do not replace a deployed jar or register this class until separately authorized and validation is complete. A future dedicated test-server registration would name the new class and its jar through XMage's normal playerTypes mechanism. This document does not activate it.

## Information and decision boundary

- `observe` extracts only own hand, public commanders, all players' life and hand counts, public battlefield and public stack information. Face-down names/rules are redacted. The immutable policy model contains no `Game`, engine card or player references.
- `getPlayable(game, true)` is intentional: in this exact upstream API, the `hidden` boolean includes this player's own hand. `false` would incorrectly omit ordinary spells and lands. It does not enable reading opponents' hands. Upstream internally makes a legality-calculation simulation copy; this adapter does not run full-state search, score that copy or expose it to the policy.
- Legal candidates come from `getPlayable` plus `getPlayableOptions`, and chosen abilities execute through `activateAbility`, retaining engine timing, cost, targeting and activation checks. Enumeration is not proof execution will succeed. A rejected activation passes instead of faking success.
- All engine priority callbacks are considered, without blanket skipping upkeep/draw/end step/opponents' turns. Mana producers are left to engine payment logic.
- Candidate scoring is capped at 128. Enumeration checks a monotonic 75 ms budget between engine calls; ranking reserves at least 5 ms. Upstream `getPlayable` and eager `getPlayableOptions` cannot be interrupted by this adapter, so this is NOT a hard wall-clock bound. Large modal/target fan-out can exceed it.
- A per-turn-step guard suppresses repeated zero-cost actions from the same source/ability. This prevents trivial loops but can conservatively omit useful repeated zero-cost actions.
- Logs expose reason, candidate count, elapsed time and activation outcome, not hidden hand contents. Runtime exceptions during priority yield a logged pass; fatal errors are not swallowed.

## Choices and limits

Own-hand mulligans use the deck plan, stop after three retries, and reset between games. Normal XMage handles the mulligan rules and bottoming; the policy does not optimize London bottoming.
Typed own-library card-selection callbacks use tutor ranking only when the engine supplies the offered cards and a non-target library choice. Typed own-hand discard and own-battlefield sacrifice callbacks likewise score only engine-eligible choices and recheck eligibility before adding them. Other choices inherit the basic bot. The creature-type helper is overridden to avoid its upstream library scan.

Combat uses `FourthSeatCombatAdapter` and its public-board policy. Complex simultaneous requirements, attack costs, planeswalker/battle attacks, commander damage and optimal multi-blocking are not solved. XMage remains the legality authority. Unsupported modal, replacement and special-card dialogs retain upstream basic behavior; compatibility is not a claim of strategic competence. No win rate, universal deck mastery or hard think-time guarantee is claimed.

Mana observations include at most 16 own-player `getManaAvailable` options (W/U/B/R/G/colorless/generic/any). These are approximate strategic hints, not payment proofs: upstream's `ManaOptions` loses conditional-mana restrictions. Computing these options makes another engine legality copy and may exceed the soft enumeration budget. Candidate mana value remains printed/base ability cost, not an advertised exact net/discounted payment; real affordability and payment are validated by XMage.

Candidate diversity: base abilities are deterministically ordered with stack interaction first, then lands, then removal, then other actions. At most eight target/modal options per base ability enter scoring, ordered by a simple public-target threat heuristic. This avoids one large target set filling the entire 128-candidate pool; truncation is still heuristic and can miss the best move. At least one non-mana candidate is retained even if engine enumeration consumes the soft budget, avoiding repeated all-budget passes in the same expensive state.

Build customization: `MAVEN_SETTINGS=/path/settings.xml` selects an existing Maven settings file; `MAVEN_REPO=/path/disposable-cache` explicitly overrides the default isolated dependency cache. Additional Maven arguments may follow the two required paths. `MAVEN` selects the executable and standard `JAVA_HOME`/`MAVEN_OPTS` apply. No TLS verification bypass is included.

Public tribe features use XMage `hasSubtype` (including changeling) for Angel, Goblin, Elf, Dinosaur and Human only. Face-down cards export no subtype labels. Persistent adapter state consists of mulligan count, last turn/step, successful-action count, zero-cost and failed-action sets, and per-source successful-activation counts. The copy constructor copies scalars and independently copies each set/map; `init` resets them. Temporary current-activation, unpaid-cost, reserved-tap-source, bounded-prefunding and optional-cost-probe contexts are restored in `finally`, reset by `init`, and copied without sharing the mutable cost. They are transient for serialization. The pinned engine normally restores player objects in place during rollback. Activation/payment `finally` blocks clear those contexts and also handle a different current engine player defensively. No policy or Game reference is stored in the player.

The isolated build now runs Maven `install` into its selected disposable dependency cache, then Maven Dependency Plugin 3.6.1 `build-classpath` with runtime scope. It writes `BUILD_DIRECTORY/Mage.Server.Plugins/Mage.Player.AI/target/fourth-seat-runtime-classpath.txt` for the real-game/soak test runners. This is a local artifact installation, not a server installation or publication. Runners must use that resolved classpath, not every jar found in the Maven cache. Dependency fetching happens during build; running tests against the resulting local artifacts needs no network.

Additional liveness guards: failed source/ability activations are suppressed for the rest of the current turn (up to 256 remembered keys, always reset next turn); no alternative is retried in the same callback after a failed activation. This is deliberately conservative: it may miss a newly affordable action later in that turn. Failure suppression is also recorded on the current engine player after rollback. Successful non-mana activations are normally limited to one per source/ability/step, Krenko and Lathril to four, and Goblin Bombardment to 64; total successful actions are capped at 64 per step. These are conservative heuristic safeguards, not rules restrictions, and can omit legal beneficial repetitions. Limits log a guard reason. Ordinary spell casts are not subject to the one-activation guard.

Redundant Equip options already attached to the chosen target are excluded via the actual EquipAbility/attachment relationship. Kamahl's identical pending animation, or a target already carrying that animation's creature/vigilance/indestructible/haste properties, is excluded. Bristly Bill's doubling is skipped when no controlled creature has a +1/+1 counter. Creature-type choices use the known commander tribe first for beneficial choices, otherwise public battlefield/own-hand counts and a stable offered choice; they never scan the library. Observation step names use the engine enum name rather than its human-readable display label. ActionKind and effect outcomes come from actual ability/effect types.

Colored multi-mana payment is specialized for the engine's typed MANA distribution callback. The adapter retains a temporary copy of the current unpaid cost during `playMana`, allocates requested colored amounts first within each offered minimum/maximum, and restores the previous payment context in `finally`. This avoids the basic AI's first-color-only allocation for Gwenna-style multi-color production. Other distribution types retain inherited behavior; conditional spending restrictions are still enforced by XMage. Keyed creature-type dialogs are handled with the actual choice-key API rather than assuming a flat choice list.

For non-mana abilities with a real TapSourceCost, payment temporarily reserves that source from both mana-producer lists, preventing spending its tap for mana and then trying to tap it again for the activation. Sacrifice-only resources are not blanket-reserved because producing mana before sacrificing them can be legal. Selected-mode effect text/outcomes and effect targets, plus selected sacrifice-cost targets, cross the immutable boundary. Candidate IDs include all cost-target IDs so different sacrifice payments remain distinct; sacrifice value is penalized before per-source truncation as well as in final policy ranking.

Mana-X announcements route through `FourthSeatVariableManaPolicy`; non-mana numeric announcements retain the inherited implementation. The helper accounts for actual X multiplicity (including XX), fixed colored costs, floating mana counted once, and engine mana-production options. Typed X-target artifact spells cap X at eligible opposing artifacts using a copied target blueprint. Conditional mana is conservatively discounted because the engine availability summary loses restrictions; specialized filtered-X costs fall back to the engine minimum. This is bounded heuristic selection with real payment validation, not exhaustive optimal X planning.

Validation checkpoint: the coherent adapter/core/helper build installed on 2026-10-16 at 10:57:56 UTC passed 92 real-XMage scenarios plus 27 helper checks using the exact generated runtime dependency classpath. Cases cover actual casts/payments, command-zone taxes, valid and invalid conditional mana, dependent Selvala payment, typed creature/color choices, selected Spree mode costs, actual Offspring tokens, sacrifice choices, source-tap reservation, X/XX payment, and a real failed-payment rollback with cleared transient contexts. This checkpoint does not establish full-game soak results or production readiness; consult the separate integration and soak reports for their actual outcomes.

Candidate affordability uses a separate engine playable-calculation snapshot: a source reserved for its own tap cost is marked tapped only in that snapshot, and actual conditional-mana restrictions are evaluated against the candidate before upstream ManaOptions erases them. Invalid conditional producer abilities and unusable conditional pool mana are removed only in the snapshot. Mixed valid/invalid outputs are conservatively excluded. This is a payment-legality calculation, not a strategic rollout; the policy never receives the snapshot. Unknown or replacement-modified mana behavior remains subject to real engine payment validation.

The pinned engine's generic alternative-cost dialog is handled only while a spell activation is in progress. An affordable normal payment is preferred; otherwise an engine-offered alternative is chosen deterministically. This is not comprehensive strategic valuation of alternate costs. Non-payment ChoiceColor dialogs rank actual public creature colors, own hand colors and commander colors instead of choosing randomly; payment-color choices retain the unpaid-cost behavior.

Selected modal costs (including Spree) are summed on an affordability-only ability copy before candidate ranking; the dispatched ability is untouched so XMage does not double-charge. Offspring is evaluated through an actual copied OffspringAbility on an engine legality snapshot, answering yes only inside a scoped probe and testing the resulting total cost. No protected-field reflection or card-text cost parsing is used. Other optional-cost mechanics are not comprehensively optimized.

The payer can preactivate a positive-net mana producer requiring mana input before consuming that input on the outer nonmana spell/ability. It checks actual unpaid demand, restrictions and producer affordability with its tap source reserved; nested prefunding is disabled and the outer unpaid-color context is restored before output allocation. Already-funded ordinary payment stays on the inherited path. This is a bounded payment-order correction, not general mana-sequence search.
